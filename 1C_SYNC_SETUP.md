# Паллета: две базы 1С → единый публичный каталог (v0.6)

**Статус на 09.10.2026:** скрипты и контракты готовы, локальные тесты PASS; реальный экспорт из 1С **не настроен**, синхронизация в Windows **не запущена**. Нельзя утверждать, что магазин автоматически публикует остатки и цены. Публичный `products.json` сейчас содержит исторические данные и статусы `unknown`.

## 1. Разделение ролей и подтверждение

| Система | Рабочая роль [Гипотеза до проверки 1С] | Данные | Не берём отсюда |
| --- | --- | --- | --- |
| **1С Розница 2** | Источник применяемой к кассе обычной розничной цены конкретной точки | Код SKU, цена за кг или упаковку, магазин, время цены | Закупочные цены, маржа, внутренние акции или клубную цену без отдельного режима |
| **1С УТ 11** | Источник **доступного для заказа** количества по этой же точке | Код SKU, доступный остаток после резерва/исключений, единица, магазин, время | Сырой общий остаток склада, транзит, резерв, товар других точек |

**Важно:** это не подтверждённая конфигурация регистров. Если в УТ нет достоверного физического остатка продающей точки или ценник на кассе задаёт иная база, распределение ролей нужно изменить **до** боевой публикации. Обе выгрузки должны использовать общий одобренный `store_key` и **один и тот же идентификатор SKU**, сопоставленный с `Номенклатура.Код для поиска`. Если коды различаются между базами, нужна одобренная таблица соответствия; автоматического совпадения по похожему названию **нет**.

## 2. Архитектура

```text
1С Розница 2 → D:\PalletaExport\retail_prices.csv ───┐
                                                     ├─> sync_1c_dual.py → products.json → git push → GitHub Pages
1С УТ 11     → D:\PalletaExport\ut_saleable_stock.csv ┘
```

Экспорт **только в локальную папку на разрешённом Windows-ПК**. В 1С никакого токена GitHub. В GitHub попадает только `products.json`, без исходных CSV. GitHub Actions **не соединяется напрямую** с 1С.

`run_1c_sync.ps1` проверяет свежесть двух файлов, делает пробный расчёт, повторяет проверку для публикации и делает коммит **только `products.json`**. Не требует постоянного сервера/API; нужны локальный Python, Git и доступ в GitHub.

## 3. Строгие форматы выгрузок

CSV `;` и UTF-8/UTF-8 BOM. **Поля должны быть только указанными.** В примерах ниже все цены и количества *тестовые*, не являются ценами и остатками Паллеты.

`retail_prices.csv` из **Розницы**:

```csv
store_key;sku_code;retail_price;price_unit;captured_at
STORE_KEY_FROM_1C;УТ-00003202;54,90;кг;2026-10-09T18:00:00+03:00
```

`ut_saleable_stock.csv` из **УТ**:

```csv
store_key;sku_code;available_quantity;stock_unit;captured_at
STORE_KEY_FROM_1C;УТ-00003202;20;кг;2026-10-09T18:04:00+03:00
```

- `store_key`: одинаковый подтверждённый идентификатор одной продающей точки в обоих файлах. В примере заглушка, заменяется после сверки.
- `sku_code`: одобренный код позиции Паллеты. Каждая строка должна иметь **одну и ту же номенклатуру и фасовку** в УТ и Рознице. Нельзя выдавать разные фасовки за один SKU.
- `retail_price`: **действующая цена обычной продажи**, положительная, в рублях, не более 2 знаков после запятой. Для `by_pack`: цена одной упаковки и `price_unit=pack`; для весового товара: цена за `unit` из `products.json` (например, `кг`).
- `available_quantity`: готовое доступное к продаже через сервис количество **после учета резервов, ограничений и страхового запаса**. Для фасовки: целые упаковки, `stock_unit=pack`; для весового: `stock_unit` соответствует каталогу. `0` обязательно выгружать, отсутствие SKU запрещено.
- `captured_at`: время фактического чтения базы с часовым поясом; **не** фиктивное время запуска Windows-скрипта. Файлы обновлять атомарно: записать временный CSV и переименовать после завершения экспорта.
- В обоих файлах на каждом цикле должны быть **все одобренные коды из публичного `products.json`** (сейчас 9 из 21; остальные пока останутся `unknown`). Лишние коды, не включённые в публичный whitelist, отвергаются.
- Оба среза должны быть моложе 20 минут и различаться по времени не больше чем на 15 минут. Отсутствие хотя бы одного SKU, ошибка единицы или магазина = **STOP**.

**Не включать:** закупочные цены, себестоимость, GP, полные остатки складов, поставщиков, телефоны, покупателей, пароли, токены. Публичный запас лучше ограничивать вниз безопасной квотой; алгоритм не резервирует его и не гарантирует наличие в момент продажи.

## 4. Настройка на Windows-ПК магазина

1. В Рознице 2 проверить **фактическую кассовую** цену 1 весового и 1 фасованного SKU для нужной точки. Уточнить вид цены, организацию, магазин и время вступления цены в действие (не подставлять непроверенный регистр).
2. В УТ 11 проверить, действительно ли там известен **доступный именно для продажи в этой точке** остаток тех же двух SKU с резервами. Если он есть только в Рознице, это другая схема и её надо явно утвердить.
3. Сверить общие коды/таблицу кодов и `store_key`; для SKU без кода не дополнять значение по названию автоматически.
4. В каждой базе настроить отдельную штатную обработку/регламентное задание, пишущее **только whitelist SKU** в указанный CSV. Записывать атомарно, с настоящим временем фактического среза.
5. На Windows установить Python 3.11+ и Git, создать `D:\PalletaExport`, клонировать `git clone https://github.com/shmlr/palleta-menu.git D:\PalletaMenu`. Создать отдельного Windows-пользователя задания с минимальными правами к папке экспортов и записи в этот **единственный** репозиторий. Не сохранять GitHub-токен в репозитории/PS1/CSV; использовать Git Credential Manager и fine-grained token с `Contents: Read/Write` только для `shmlr/palleta-menu`.
6. **Тест** только после двух реальных экспортов (подставьте согласованный ключ):

```powershell
cd D:\PalletaMenu
py sync_1c_dual.py --prices D:\PalletaExport\retail_prices.csv --stock D:\PalletaExport\ut_saleable_stock.csv --store-key "ВАШ_СОГЛАСОВАННЫЙ_STORE_KEY" --dry-run
```

7. Если PASS, проверьте единицы, кассовую цену и реальные остатки на двух SKU, затем ручной запуск:

```powershell
powershell.exe -NoProfile -File D:\PalletaMenu\run_1c_sync.ps1 -StoreKey "ВАШ_СОГЛАСОВАННЫЙ_STORE_KEY"
```

8. В Планировщике Windows запустить `run_1c_sync.ps1` каждые 30 минут **через несколько минут после завершения обеих выгрузок 1С**. Запрещать параллельные запуски. Две базы должны быть в пределах установленного окна 20/15 минут. Если задержка, ошибки или несовместимые SKU — STOP без публикации.

**Важно:** запуск интеграции в штатном режиме допустим только после двух проверенных контрольных выгрузок с реальными данными. Если персонал обязан проверять каждое изменение цены, вводится ручной gate перед git push; автоматизация не должна обходить эту процедуру.

## 5. Контроль и критерии готовности

- [ ] Подтверждён реальный источник цены в Рознице (сверено с кассой).
- [ ] Подтверждено, что УТ даёт **продаваемый** остаток именно выбранной точки.
- [ ] Согласованы идентификатор точки и код SKU между базами.
- [ ] Подтверждены фасовка, единица, нулевой остаток на 2–3 контрольных товарах.
- [ ] Два свежих CSV содержат полный одобренный whitelist (сейчас 9/9).
- [ ] Локальный `--dry-run` PASS и ручной запуск с фиксацией коммита PASS.
- [ ] В браузере видно новое время обновления и корректный статус наличия.
- [ ] Проверен контрольный OOS: если в источнике 0, меню берёт допустимый аналог или другое блюдо.
- [ ] Настроен мониторинг ошибок планировщика и провала публикации Pages.
- [ ] Все 21 SKU снабжены сверенными кодами либо отмечены как недоступные для автокорзины.

**Эксплуатационное ограничение:** GitHub Pages обновляется не мгновенно; корзина не резервирует товар, конечную цену, наличие и доставку подтверждает сотрудник магазина. При недоступной или устаревшей выгрузке сервис должен показывать «уточняется», не выдавать остаток за текущий.
