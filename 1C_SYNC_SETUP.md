# Паллета: одна база УТ 11 → публичный каталог GitHub Pages

**Решение владельца, 09.10.2026:** цены передаются **из УТ 11 в Розницу**. Поэтому для сервиса «Меню на неделю» используем **только УТ 11** для выгрузки подтверждённых розничных цен и доступных к заказу остатков. Отдельный поток из Розницы не нужен.

**Фактический статус:** алгоритм, скрипт проверки CSV и публикация через GitHub подготовлены. Экспорт из рабочей базы УТ и Планировщик заданий Windows **не настроены и не запускались**. Сервис ещё не получает реальные остатки автоматически.

## Подтверждено 10.10.2026: вид цены

По скриншоту владельца в УТ 11 показаны «Закупочная, RUB», «Розничная, RUB», «Оптовая, RUB». Для публичного меню выбран **«Розничная, RUB»**. Закупочный и оптовый виды не выгружать.

В Windows-скрипте `run_1c_sync.ps1` значение `-PriceType` по умолчанию теперь **`Розничная, RUB`**. В CSV поле `price_type` должно дословно совпадать с этой строкой. Если УТ хранит **название вида «Розничная» и валюту RUB отдельно**, обработка выгрузки должна нормализовать *оба поля вместе* к `Розничная, RUB`, только после проверки реквизитов 1С. Не подставлять вручную другой вид цены, не брать цену из случайного поля отчёта.

**Осталось проверить:** привязку розничного вида цены к торговой точке, фактическое применение цены на кассе и точный склад/показатель доступного остатка УТ. По одному снимку списка видов цен эти факты не устанавливаются.

## 1. Что нужно подтвердить в УТ 11 перед началом

1. **Вид цены.** Определить точный вид розничной цены, который из УТ передаётся в Розницу и применяется в обычной продаже. В УТ могут быть и закупочные, и клубные, и другие виды цен: их нельзя публиковать вместо стандартной цены. Сверить 2–3 SKU с чеком/кассой до запуска. Специальные скидки и клубные цены пока не считаем.
2. **Магазин и склад.** Выбрать именно продающую точку Паллеты, а не весь склад и не остатки других магазинов. Определить реальный `store_key`.
3. **Доступный остаток.** Учитывать резерв, брак, непригодный к продаже остаток, страховой запас. Если в УТ нет правдивой доступности товара на полке, нельзя выдавать его за «в наличии»; нужно сначала наладить обмен/сверку.
4. **Коды.** `sku_code` из поля `Номенклатура.Код для поиска`, соответствие фасовки. Сейчас сопоставлено 9/21 товаров; по остальным код неизвестен. Не сопоставлять автоматически только по похожему названию.

## 2. Архитектура

```text
             локальный компьютер магазина
┌──────────────────────────────────────────────────┐
│ 1С УТ 11: вид обычной розничной цены +          │
│ доступный остаток конкретной точки              │
│          ↓ выгрузка каждые 30 минут             │
│ D:\PalletaExport\ut_public_catalog.csv           │
│          ↓ строгая проверка CSV                 │
│ sync_ut_catalog.py → products.json             │
│          ↓ git push                            │
└──────────────────────────────────────────────────┘
                 ↓ GitHub Pages
    https://shmlr.github.io/palleta-menu/
```

Розница остаётся для кассы и выборочной сверки, но не участвует в регулярном обмене с сервисом меню. GitHub Actions не подключается к внутренней 1С. Цена на кассе и остаток при подтверждении заказа могут измениться после последней выгрузки.

## 3. Формат **единственной** CSV из УТ

UTF-8 или UTF-8 BOM; разделитель `;`. Заголовки строго в указанном порядке:

```csv
store_key;sku_code;price_type;retail_price;price_unit;available_quantity;stock_unit;captured_at
STORE_KEY_FROM_1C;УТ-00003202;PRICE_TYPE_FROM_UT;54,90;кг;20;кг;2026-10-09T18:00:00+03:00
```

**Все значения во второй строке — демонстрационные, не факты Паллеты.** Заменить `store_key`, `price_type`, розничную цену, остаток и время на проверенные данные УТ. Время должно отражать фактический момент среза с часовым поясом. Использовать атомарную запись (временный файл → переименование), не выдавать старый файл за новый.

- `sku_code`: тот же код, что в утверждённом публичном `products.json`; не 1С ссылка и не штрихкод, если не согласовано другое сопоставление.
- `price_type`: **ровно один** утверждённый вид обычной розничной цены, один и тот же для всех строк; скрипт требует соответствия параметру `-PriceType`.
- `retail_price`: действующая цена, рубли (две цифры после запятой максимум). Фасованные позиции: цена одной потребительской упаковки, `price_unit=pack`. Весовые: цена за `кг`/другую соответствующую единицу.
- `available_quantity`: ограниченный объём, реально доступный к продаже, а **не полный сырой остаток**, с учётом резервов, брака и страхового запаса. Фасованные позиции: целые упаковки и `stock_unit=pack`.
- `captured_at`: фактический момент выгрузки; не старше 20 минут во время импорта. Каждая выгрузка содержит **все 9 сопоставленных SKU**, в том числе позиции с нулевым остатком. Неизвестные позиции не публикуются.

В GitHub не допускаются закупочные цены, наценка, GP, поставщики, личные данные, полные внутренние остатки, пароли и исходные CSV. Допускается публикация только одобренных данных о конкретных SKU.

## 4. Запуск Windows после настройки экспорта УТ

1. Установить Python 3.11+ и Git на ПК с доступом к УТ 11. Создать `D:\PalletaExport`; установить права доступа. Настроить ограниченную запись в **один** репозиторий `shmlr/palleta-menu` через Git Credential Manager или иной согласованный безопасный механизм. Не хранить токен в скрипте.
2. Клонировать: `git clone https://github.com/shmlr/palleta-menu.git D:\PalletaMenu`.
3. Настроить регламентную обработку УТ, экспортирующую **один** CSV `D:\PalletaExport\ut_public_catalog.csv` каждые 30 минут. Реальные регистры УТ, вид цены, точку и доступный остаток определить после проверки базы.
4. Первый прогон (без записи):

```powershell
cd D:\PalletaMenu
py sync_ut_catalog.py --csv D:\PalletaExport\ut_public_catalog.csv --store-key "РЕАЛЬНЫЙ_КЛЮЧ_ТОЧКИ" --price-type "Розничная, RUB" --dry-run
```

5. Только после `PASS` и сверки 2–3 товаров, ручной запуск:

```powershell
powershell.exe -NoProfile -File D:\PalletaMenu\run_1c_sync.ps1 -StoreKey "РЕАЛЬНЫЙ_КЛЮЧ_ТОЧКИ" -PriceType "РЕАЛЬНЫЙ_ВИД_ЦЕНЫ"
```

6. В Планировщике заданий Windows выполнять команду из пункта 5 **каждые 30 минут** через несколько минут после регламентной выгрузки УТ. Не допускать параллельных запусков, настроить журнал ошибок и контроль отсутствия новых публикаций.

## 5. Пороговые проверки

- Достоверный `store_key` точки и выбранный `price_type`.
- Все сопоставленные 9/9 кодов присутствуют, одинаковый вид цены и магазин на каждой строке, нет дубликатов и лишних SKU.
- Цена больше нуля, максимум две десятичные цифры; фасованный остаток — целое количество; единицы соответствуют каталогу.
- Время реальной выгрузки моложе 20 минут, есть смещение часового пояса.
- Ошибки любого вида = STOP без нового коммита. На сайте старые остатки через срок свежести станут «уточняются».
- Тест нулевого остатка: ноль в тестовом CSV приводит к предложению замены SKU или другого блюда. **Тестовые остатки никогда не загружать на публичный GitHub.**

## 6. Ограничения и готовность

Пока **не сделаны**: регламентная выгрузка из реального УТ, проверка вида цены, заполнение кодов оставшихся 12 SKU, контрольный dry-run на настоящих данных, настройка Планировщика. Автоматический заказ/резервирование и оплата не предусмотрены.
